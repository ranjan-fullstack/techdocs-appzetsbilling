5. Infrastructure implications for the roadmap

  • Single point of failure: app, DB, cache and files live on one 2 vCPU host. Adequate for the current footprint (39 businesses, 77 sales rows, see Part 02) but not for multi-outlet chains or Odisha-wide scale.
  • Two dormant capabilities need switching on before any new feature ships: a Laravel scheduler cron and a supervised queue worker. Almost every proposed module (WhatsApp, aggregator sync, campaigns, reservations reminders, low-stock alerts) depends on them.
  • Cert renewal, log rotation, uptime monitoring and offsite file backup are the cheapest reliability gains.

See Part 04. 3.2 AppZetBilling today VERIFIED

Server-rendered cloud application on one VPS. No service worker for the POS, no IndexedDB, no local database, no sync engine, no idempotency keys on sale creation. If the internet drops, billing stops. Moreover, VERIFIED AcnooInvoiceController::newInvoice builds the sales invoice number as (sales count + KOT count) + 1 per business: it is racy under concurrent sales, and because a sales.delete-all route exists, deleting rows can cause numbers to be re-issued. This must be fixed before any offline design because offline devices multiply the collision risk.

3.3 Proposed architecture RECOMMENDED

Level 0  Harden the online path (prerequisite)
  - server-side invoice sequence per outlet (row-locked counter)
  - client_uuid on every sale/KOT write (unique per business) -> duplicate-proof retries
  - queue worker + scheduler running

Level 1  Offline-tolerant web POS  (fast, no new hardware)
  - PWA + service worker caches app shell, menu, tables, taxes, payment types
  - IndexedDB "outbox": new sale / KOT / payment operations queued with client_uuid,
    device_id, local sequence, timestamp
  - reads served from cache; writes queued when offline, replayed in order on reconnect
    via POST /sync/batch (idempotent, per-operation result)
  - printing: local print agent works without internet (LAN printers)
  - limits: one active device per table while offline; bill number = outlet prefix +
    device prefix + local counter (reconciled to official number after sync)

Level 2  Outlet server (only for customers who need days offline / multi-device offline)
  - small local service (Windows/Linux mini-PC) with SQLite/MySQL mirror of one outlet
  - devices talk to the local server on the LAN; it syncs to the cloud (pull config,
    push transactions) with the same batch API
  - this is the closest analogue of Petpooja's Bridge Server; costly to support

Conflict and duplicate rules

  • Duplicates: unique (business_id, client_uuid) on sales/KOT/payments; a replay returns the original result.
  • Ordering: operations carry a device sequence; server applies per-entity in sequence; a table opened on two offline devices becomes a conflict item for a manager to merge (uses the same merge feature as table merge).
  • Master data (menu/price): server wins; device pulls changes?since= on reconnect.
  • Stock: deductions are applied on sync (ledger style); negative stock allowed offline, flagged after.
  • Payments: cash/UPI-manual payments queue offline; gateway payments require connectivity and are not attempted offline.
  • Retry: exponential backoff, visible "unsynced" counter, manual "sync now", alert if unsynced older than N hours.
  • Offline KOT: kitchen printer on LAN prints without cloud; a KDS needs LAN or connectivity (Level 2).
Priority note Offline is a CRITICAL capability gap against Petpooja's documented core offering and a top concern for low-connectivity towns, but Level 1 is roughly a quarter of engineering work and Level 2 is a product line of its own. Recommendation: build Level 0 immediately, Level 1 in Phase 1–2, and defer Level 2 until customer demand is measured.

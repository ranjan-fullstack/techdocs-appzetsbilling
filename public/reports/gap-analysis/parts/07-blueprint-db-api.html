Everything on this page is a RECOMMENDED proposal derived from the verified AppZetBilling stack (Laravel 10, MySQL, Redis, nwidart modules, Sanctum, /api/v1 REST with kebab-case plural resources). Nothing was created or altered in the database. Conventions matched from the codebase: business_id on every tenant table, nullable branch_id for outlet scope, status tinyint, Laravel timestamps, new features as nwidart modules gated through plans.available_modules.

Two prerequisites for almost every item below (both verified missing today, see Part 01): (1) a schedule:run cron, (2) a supervised queue:work worker with a Redis queue instead of the empty database queue. Without them, WhatsApp sends, aggregator sync, campaigns, low-stock alerts and reminders cannot run reliably.

5. API gap analysis (Phase 18)

RECOMMENDED Follow the existing style: prefix /api/v1, auth:sanctum + module + active.branch middleware, plural kebab-case resources, apiResource where CRUD fits. Public/partner endpoints use a separate auth:api-key guard with scopes. Inbound webhooks live under /api/v1/webhooks/{provider} with no session/CSRF, signature-verified, tenant resolved from the payload identifier.

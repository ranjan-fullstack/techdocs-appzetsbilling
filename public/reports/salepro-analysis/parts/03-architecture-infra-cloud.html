7. Tenant architecture

What SalePro SaaS actually does VERIFIED FACT

One landlord (super-admin) database plus one MySQL database per tenant, created automatically through cPanel/Plesk/PlanetHoster API or, on a VPS, MySQL root access. Tenants are found by subdomain or custom domain. Tenant DB backups and updates are triggered from the client list. Migrating a standalone SalePro into a tenant is a data-only import that excludes roles/permission tables.

8. Server requirements

Sizing method ASSUMPTION: a POS tenant is a light OLTP workload — a single-outlet shop peaks at ~1–3 requests/second per active register, mostly reads plus one write per bill. Only 10–30% of tenants are peak-active concurrently (evening rush overlaps for restaurants). Tenants per DB: average DB size 50–200 MB after year 1 ASSUMPTION.

Minimum viable production (up to ~100 tenants)

  • 4 vCPU / 8 GB RAM / 80–160 GB NVMe, Ubuntu LTS, Nginx + PHP-FPM 8.3 (OPcache), MySQL 8 (root access for the add-on), Redis (cache/session/queue — recommended even though not required), Supervisor queue worker, a per-minute cron, Let's Encrypt wildcard cert via DNS-01 with an API hook, daily off-site encrypted backups, uptime + cert-expiry monitoring.
  • Wildcard DNS: *.yourdomain A/AAAA record. Custom domains need per-domain certs that the add-on does not auto-issue VERIFIED FACT → plan Caddy/Traefik/certbot automation or Cloudflare for SaaS.
  • Lesson from your own audit: wildcard cert renewal was manual DNS-01 without a hook and would have expired (memory: gap-analysis Priority 0). Automate before onboarding paying customers VERIFIED FACT.

When to move off a single VPS RECOMMENDATION

  • CPU sustained > 60% at evening peak, MySQL buffer-pool hit < 98%, open_tables churn, or backups no longer finish in the nightly window → split DB from app (~150–300 tenants).
  • Any single server whose loss would take > 1 hour to restore → add replicas/standby (~500 tenants or first enterprise/SLA customer).
  • Above ~1,000 tenants the add-on's "Update Client DB" loop and file-per-table counts (≈ 100k+ tables) become the bottleneck: add sharding and a migration runner (custom work; the add-on does not document one UNKNOWN).
  • Above ~5,000 tenants a per-tenant-DB-on-one-MySQL design should be considered end-of-life for the core; expect dedicated platform engineering.

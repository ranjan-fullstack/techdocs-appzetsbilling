PART 01

Executive Summary

Web and mobile are already one platform, not two disconnected systems: both are verified clients of the same Laravel 10 backend, the same MySQL database, and — for roughly 80–85% of the shared operational surface — the same /api/v1 REST API. This is the headline finding of this audit and it changes the shape of the work ahead: the task is to complete and harden an integration that already exists, not to build a bridge between two divergent systems.

Mobile is a well-built Flutter app (Riverpod, Dio, auto_route) with genuinely strong custom engineering — including an in-house receipt-layout engine for thermal printing — and a nearly complete feature set matching the backend's tenant-facing modules (POS, KOT, kitchen, inventory, HRM, reports). Its real gaps are integration and operational, not architectural: no offline support, a single hardcoded production URL, a debug-signed release build, and several already-existing backend endpoints (token refresh, password change, module entitlement check) that the app simply doesn't call yet.

Backend is a Laravel 10 / Sanctum / MySQL SaaS (a customized "Acnoo" template, module-based via nwidart/laravel-modules) that already enforces multi-tenant isolation via business_id/branch_id scoping, though that isolation currently depends on per-controller discipline rather than a structural guarantee — the single highest-priority hardening item in this report. Queueing and the task scheduler are configured but not actually running in production; realtime broadcasting is scaffolded but not provisioned.

The two structural gaps — not incremental ones — are that Multi-branch and Cash Register are fully built backend modules with zero mobile presence. Everything else in the API mapping (§7) is either already shared or a small, well-scoped addition.

One open question materially affects how this roadmap should be sequenced and could not be resolved from a read-only pass alone: whether the web business panel calls its own /api/v1 API internally or runs parallel Blade-only business logic. Resolving this should be the very first step, before the phased roadmap (§20) begins.

Bottom line: continue with Flutter; do not rebuild the mobile app or the backend. Spend the first phase on tenant-isolation hardening, CI/CD, and mobile's own foundation (environment config, secure token storage, release signing) — all low-effort, high-leverage — then build multi-branch support on mobile and, as the largest single effort in this roadmap, offline order queueing. Full detail, evidence, and a phase-by-phase plan with effort estimates follow in §2–§24.

Mobile-side architecture gaps

  • No offline support — connectivity_plus only blocks the UI on disconnect; no local DB, no request queue, no write cache. Significant for a restaurant POS.

  • Thin automated test coverage (6 files) relative to app size.
PART 04

Current Backend/API Architecture

A single REST API, versioned once under Route::prefix('v1') in routes/api.php (no v2 exists yet). No GraphQL. Auth is Sanctum bearer tokens for the API; the admin/business web panel uses classic session auth.

Request pipeline (tenant-scoped API routes)

Request
  -> auth:sanctum (Sanctum bearer token -> resolves the User)
  -> module (CheckModuleAccess: is this feature enabled on the tenant's subscription plan?)
  -> active.branch (CheckActiveBranch: resolve/require the user's active branch)
  -> [expired] (ExpiredMiddleware, on write routes: block if the tenant's plan has lapsed)
  -> Controller -> business_id/branch_id-scoped query -> JSON response

Public storefront routes instead go through ResolveBusiness, which resolves the tenant from a verified custom domain (CustomDomainAddon) or a restaurant_slug route parameter, binding it as currentBusiness — relevant if online ordering/customer-facing features are built out later.

Tenant isolation enforcement

Tenant isolation is shared-database, discriminator-column based (not schema-per-tenant, no stancl/tenancy). Nearly every domain table carries business_id (cascade-deleted with the tenant) and most also carry branch_id. Isolation is enforced at the controller/query layer, not via Eloquent global scopes — no global scope class was found; every controller must remember to filter by auth()->user()->business_id. This is functional today but is a maintainability/security risk as the codebase grows (see §15 Security Findings).

Modules (feature areas), each a self-contained Laravel module via nwidart/laravel-modules

ModuleCovers
Core app (routes/api.php)Auth, business/profile, dashboard, parties, products, sales, purchases, quotations, dues, expenses, incomes, payment types, plans, taxes, transactions, staff, roles/permissions, coupons, KOT, kitchens

Each module's routes are gated the same way (auth:sanctum + module), and module availability itself is gated a second time by the tenant's subscription plan (plan_subscribes.available_modules JSON), independent of whether the module is installed on the server — i.e. every tenant shares one codebase/deployment, but features are entitlement-gated per plan.

Admin (SaaS-operator) panel

routes/admin.php, session-auth + admin middleware, fully separate from tenant business users: manages tenants (business CRUD, plan upgrades), subscription approvals, business categories, global roles/permissions, system/domain settings, the addon marketplace, payment-gateway configuration, currencies, and the marketing CMS. This is a third distinct actor type beyond "tenant staff" and "storefront customer" — relevant when scoping mobile access (mobile currently only needs the tenant/staff surface).

Background processing

  • Queue: QUEUE_CONNECTION=database is configured, but no worker process runs (no artisan queue:work, no Supervisor) — any code path that dispatches a job today would silently pile up in the jobs table unprocessed. Needs an operational fix before anything (e.g. report generation, notification fan-out) is safely moved to a queue.
  • Scheduler: Kernel.php schedules ingredient:check-low-stock every minute, but no crontab invokes artisan schedule:run anywhere on the box — this scheduled task is very likely not firing in production today.
  • Realtime: BROADCAST_DRIVER=pusher is wired in config and routes/channels.php defines one private channel (App.Models.User.{id}), but Pusher credentials are empty and no broadcast server (Pusher/Soketi/Echo) is running — the capability exists in code but is dormant.
PART 05

Database Architecture

Percona Server 8.4.10-10 (MySQL-compatible), database appzetsbilling, 97 tables, single shared schema (no schema-per-tenant). Representative row counts confirm an early-stage/low-volume production instance: 39 tenant businesses, 55 users, 327 products, 77 sales, 872 notifications.

Tenant chain

business_categories -> businesses -> branches -> users / staff
                                              -> roles / permissions (Spatie, polymorphic)

businesses is the tenant root (has plan_subscribe_id). branches cascade-deletes from businesses. users (login accounts) carry business_id, branch_id, and active_branch_id. staff is a separate, lighter HR record (business_id only) used by HrmAddon — distinct from users. Roles/permissions use spatie/laravel-permission's standard polymorphic pivot tables (model_has_roles, role_has_permissions, model_has_permissions), matched by model_type/model_id, not a direct FK to users.

Product -> order chain

categories -> products -> sale_details <- sales <- parties / tables / taxes / coupons / payment_types

All cascade from businesses. There is no separate invoices table — an "invoice" is a view over sales (sales.invoiceNumber is the identifier); the mobile app's and web admin's "Invoices" screens both read/write the same sales rows.

Purchasing chain (mirrors sales)

parties (type=supplier) -> purchases -> purchase_details -> ingredients / units

Finance

payment_types (tenant-configurable label list, not a gateway integration) is referenced by both sales and purchases. transactions is the unified ledger across both (sale_id / purchase_id nullable FKs + a type column) — this is the single source of truth for money movement per tenant.

SaaS subscription/billing (distinct from tenant POS billing)

plans -> plan_subscribes -> gateways
            ^
         businesses

plan_subscribes snapshots the plan's limits and available_modules at subscribe-time, so a later plan change doesn't retroactively alter an already-subscribed tenant's entitlements — important to know before building any mobile "upgrade plan" flow.

Key relationship takeaway for mobile integration

Every core business object (products, sales, purchases, parties, staff, etc.) is already business_id-scoped (and mostly branch_id-scoped) in the schema. A mobile client that authenticates via the same Sanctum flow and hits the same /api/v1/* routes inherits this isolation automatically — there is no separate mobile data model to reconcile; mobile and web are structurally reading/writing the same rows today, mediated by the same controllers.

PART 09

Current Architecture Problems

Cross-cutting (Web + Mobile)

  1. Whether the web panel actually consumes its own REST API is unconfirmed. If the Blade admin/business panel has separate controllers that duplicate the business logic already in the Api/ controllers (rather than calling /api/v1/* internally), the team is maintaining tax/discount/stock logic in two places today — a correctness risk (the two can silently drift) independent of mobile. Action: have the web team confirm this directly, it changes how urgent an "API-first" refactor is.
  2. Tenant isolation is enforced by controller-level business_id filtering, not Eloquent global scopes. It works today, but it means every new controller/endpoint (including future mobile-only ones) must remember to scope its queries — one missed where('business_id', ...) is a cross-tenant data leak. This is the single most important thing to fix before scaling the API surface.
  3. No CI/CD pipeline. The production app root is a git working tree pulled/pushed to directly (git remote -v shows a live GitHub origin, recent commit made straight on the VPS). No staging environment, no automated tests gating a deploy, no build artifact.

Backend-specific

  1. Configured-but-inert infrastructure: queue (QUEUE_CONNECTION=database with no worker running), scheduler (schedule:run not in any crontab, so the low-stock check likely never fires), and realtime broadcasting (Pusher wired in code, no credentials, no broadcast server). None of these are wrong to have configured, but building new features that assume they work (e.g. "push a realtime order update") will silently do nothing today.
  2. Wide-open CORS (allowed_origins: ['*']) on api/*. Lower risk because the API is bearer-token, not cookie/credentialed, but still broader than necessary and worth tightening once mobile's environment strategy (§16) introduces named client origins/apps.
  3. LOG_LEVEL=debug in production and a world-writable storage/logs/ directory — minor but easy hardening fixes.
  4. Single API version (v1) with no versioning strategy yet. Fine today with one mobile client version in the wild, but there is no mechanism in place for the moment a mobile v2 needs a breaking change while v1 users still exist.

Mobile-specific

  1. No offline support at all for a restaurant POS — the single biggest functional gap for real-world restaurant conditions (spotty Wi-Fi, router restarts, busy service). See §14.
  2. Production APK is signed with the debug keystore. A real release-signing config needs to exist before a genuine Play Store/App Store release, independent of any architecture work.
  3. Hardcoded single production URL, no environment split. Every dev/staging test today either hits production or requires editing source and rebuilding — high risk of an engineer accidentally testing against live tenant data, and no safe way to test backend changes against a mobile build before release.
  4. No refresh-token usage, no FCM token-refresh sync, unencrypted token storage. The backend already exposes /refresh-token; mobile's auth session handling should be upgraded to use it rather than relying solely on a long-lived bearer token in plain shared_preferences.
  5. Two whole backend modules (Multi-branch, Cash Register) have no mobile presence. Not a bug, but a scope decision that should be made deliberately (§11/§20) rather than left as an accidental gap.

Net assessment

The good news for this audit: mobile and web are not two disconnected systems with separate databases or separate business logic — they already share one Laravel backend, one MySQL database, and (for the bulk of tenant-facing features) the same versioned REST API. The real work is tightening and completing an already-shared architecture, not building bridges between two divergent ones.

PART 12

Multi-Tenant Strategy

Business (tenant) -> Branch -> User (staff) -> Role -> Permission
                            -> Staff (HR record, distinct from User)

Isolation must be enforced server-side, and today it is — but fragile-ly. Every domain table carries business_id (most also branch_id), and API routes are gated by auth:sanctum → module → active.branch middleware. Mobile never sends a tenant ID on requests; the backend resolves it from the authenticated user via the Sanctum token, which is the correct pattern — the client is never trusted to declare its own tenant, and mobile should never be changed to do so.

The gap is that isolation is currently achieved by every controller remembering to filter by business_id/branch_id, not by a structural guarantee (no Eloquent global scope was found). As the API surface grows to serve mobile more fully, a single missed filter in a new or edited controller is a cross-tenant data leak.

Recommended hardening (backend, before/alongside expanding the API)

  1. Add a global scope or base-model trait that automatically constrains every tenant-scoped model's queries to the authenticated user's business_id (and branch_id where applicable), so isolation is the default, not something to remember per-controller.
  2. Add authorization tests (§18) that specifically try to access another tenant's products/sales/parties/etc. by ID and assert 403/404 — this is the highest-value test category for a SaaS product and currently appears untested on either side.
  3. Keep permission checks (spatie) server-side as the enforcement layer; mobile's client-side PermissionModules/hasFullAccess checks are correctly used for UI gating only — confirm no endpoint trusts a client-sent permission flag instead of re-checking server-side.
  4. Admin (SaaS-operator) vs. tenant vs. storefront-customer are three separate guards today (admin, Sanctum tenant user, customer.auth) — keep mobile strictly within the tenant-staff guard; never let a future "multi-tenant admin app" reuse the staff app's token scope.

No architectural tenant model change is needed — the shared-database, discriminator-column design is appropriate at this scale (39 tenants, low transaction volume); a schema-per-tenant or dedicated multi-tenancy package would add operational cost without a corresponding isolation benefit here.

PART 13

Realtime Strategy

Today: no realtime channel is actually live. BROADCAST_DRIVER=pusher is configured in .env and one private channel (App.Models.User.{id}) is defined in routes/channels.php, but Pusher credentials are empty and no broadcast server runs — it's scaffolding, not a working feature. The only "realtime-ish" behavior today is FCM push notifications, and even those are triggered manually per-event by application code, not by a generic model-change broadcaster.

Where realtime actually matters here

  • Mobile creates an order/KOT → web dashboard should reflect it promptly. Kitchen/table turnaround is time-sensitive.
  • Web POS changes an order/KOT status → mobile (kitchen or waitstaff view) should reflect it promptly.
  • Everything else (reports, HRM, settings, inventory levels outside of a live order) tolerates normal request/response latency and does not need push-based realtime.

Recommendation: don't build a general WebSocket layer yet — use what's cheapest for the two flows that need it

  1. KOT/order status changes: use FCM data messages (already integrated on both the backend, via kreait/laravel-firebase, and mobile, via firebase_messaging) to notify "an order/KOT changed" and have the receiving client re-fetch that resource from the REST API. This is exactly the pattern the mobile app already has partially working (KOTOrderModifiedAE fired from push data) — extend it to fire on every KOT/order mutation from the backend side, and add the same trigger for the web dashboard (a lightweight polling fallback, e.g. every 10–15s on the active order/KOT screens, is a reasonable web-side complement without adding new infrastructure).
  2. Everything else: plain REST, refetched on navigation/pull-to-refresh, as today.
  3. Only if/when push-through-FCM proves too laggy or unreliable in practice (e.g. multiple kitchens, high order volume) is it worth finishing the Pusher/Soketi setup for true low-latency WebSocket broadcasting of order/KOT events specifically — keep the channel authorization pattern already scaffolded in channels.php as the starting point, and scope it to order/KOT/table channels only, not a general-purpose event bus.

This avoids standing up and operating a WebSocket server for a 39-tenant, low-volume SaaS before there's evidence it's needed, while still closing the actual gap (web and mobile currently have no way to learn about each other's order/KOT changes without a manual refresh).

PART 14

Offline Strategy

Today: fully online-only. connectivity_plus only shows a blocking "no internet" dialog; there is no local database, no write queue, no cache. Confirmed no SQLite/Hive/Isar/Drift dependency anywhere in the mobile codebase.

Recommended scope — deliberately narrow, not a general offline-first rewrite

Should work offlineMust require internet
Viewing recently-loaded product/menu list (read-only cache)Sign-in (first time)
Building a cart/order locallyFinal order submission/confirmation
Viewing the last-synced table/KOT statePayment processing
Reprinting a receipt already generated on-deviceInventory/stock adjustments
Reports (always live)

What data should be cached

Only reference/catalog data that changes slowly and is safe to read stale for a few minutes: products, categories, modifiers, tax rates, tables/areas, payment types. Not stock levels, not prices if dynamic promotions exist, not anything transactional.

Queueing orders

  • A locally created order/KOT gets a client-generated idempotency key (UUID) at creation time, stored with the queued request.
  • On reconnect, queued writes replay in creation order against the existing POST /sales / POST /kots endpoints.
  • Backend change required: accept and de-duplicate on that idempotency key (e.g. a unique constraint or lookup on a client_reference_id column before insert) — this is the one piece of backend work offline support actually needs, and it directly prevents duplicate orders from a retried/re-queued submission.

Conflict resolution

Keep it simple given the domain: orders/sales are append-only from the client's perspective (a queued order either succeeds once or is rejected, never merged), so there's no real multi-writer conflict to resolve for order creation. The one place a conflict can occur is stock: if two devices queue orders against the same low-stock item while offline, the backend's normal stock-deduction logic (already server-side, per §5/§9) is the tie-breaker — last-write-wins at the database is acceptable; do not attempt client-side stock reconciliation.

Invoice numbering

Must remain server-assigned, never client-generated — sales.invoiceNumber is already generated backend-side; an offline queue must not pre-assign invoice numbers locally, only a local, disposable reference (the idempotency key above) until the server confirms and returns the real number.

Failed payments

A payment that fails or is ambiguous while offline should not be queued for silent retry — payment confirmation should always require being back online and should surface an explicit "payment not confirmed, please retry" state rather than assume success.

This is intentionally a local storage engine (e.g. drift/sqflite) + a small outbox table + one backend idempotency change, not a full sync-framework rebuild — appropriate for a POS where the offline window is realistically minutes, not hours.

PART 17

API Versioning Strategy

Today: a single v1 prefix, no version negotiation, no v2. This is fine right now because there's effectively one mobile client version in the field, but it has no mechanism for the moment that changes.

Recommendation — additive-first, version bump only for breaking changes

  1. Prefer backward-compatible changes within v1: add new optional fields/endpoints rather than changing existing response shapes or removing fields. This covers the large majority of near-term work in this roadmap (branches, cash register, refresh-token adoption) without needing a new version at all.
  2. Reserve a v2 prefix for genuine breaking changes (renamed/removed fields, changed auth flow, restructured resources) — mirror the existing Route::prefix('v1') pattern with Route::prefix('v2'), letting both run side-by-side.
  3. Old mobile versions must keep working against v1 for a defined deprecation window (recommend 6–12 months given restaurant staff don't always update apps promptly) after v2 ships — track this with app-version telemetry (currently absent, see §15 crash/analytics gap) so the team knows when it's safe to sunset v1.
  4. Add a minimum-supported-app-version check at login (a simple min_version field returned by /sign-in or a dedicated /app-config endpoint) so a hard-breaking mobile update can prompt an in-app "please update" message rather than failing silently against a v2-only backend.

This keeps versioning proportionate to the SaaS's actual size (39 tenants) — no need for content-negotiation headers or a formal deprecation-registry system yet, just the discipline to bump the prefix only when compatibility actually breaks.

PART 18

Testing Strategy

Today: both sides are thinly tested. Mobile has 6 test files (mostly card widgets + one strong unit-test suite for unit-price conversion) against ~180+ page directories. The backend ships phpunit scaffolding but this audit did not find evidence of a meaningful test suite either (not confirmed either way — worth a direct follow-up with the backend team).

Backend

  • Unit tests: pricing/tax/discount calculation, stock deduction logic, plan-limit enforcement.
  • Integration tests: full request-response cycles for the core POS flow (create sale → stock deducted → transaction recorded → KOT created).
  • API tests: one test per endpoint group in §7 asserting shape + status codes, especially for the newly-adopted mobile endpoints (refresh-token, change-password, module-check).
  • Authorization/tenant-isolation tests (highest priority, currently absent): authenticate as tenant A, attempt to read/write tenant B's products/sales/parties/etc. by ID, assert rejection. This is the single most valuable test category for this product.

Web

  • Component tests for the Blade/Alpine interactive pieces (order builder, KOT board).
  • E2E (e.g. Laravel Dusk or Playwright) for the core POS flow through the actual UI.

Mobile

  • Unit tests: expand beyond the existing unit-price-calculator pattern to repository/parsing logic (model fromJson, permission-flag logic, cart/order total calculation).
  • API integration tests: repository methods against a mocked Dio client (add mocktail, currently absent) for each endpoint in §7.
  • Widget/UI tests for the core POS screens (order entry, KOT board, payment).
  • Offline tests (once §14 is built): queue-then-reconnect flows, duplicate-prevention via idempotency key.
  • Sync tests: order created on mobile appears correctly via the web-side API; order/KOT status changed via web is correctly reflected when mobile re-fetches/receives push.

End-to-end (cross-app), the highest-value additions given today's near-zero coverage

  1. Mobile creates an order → assert it's visible via the same read endpoint the web panel would use → assert stock decremented correctly.
  2. Web (or a second mobile session) updates KOT/order status → assert the first mobile session receives the update (push-triggered refetch, per §13) within an acceptable delay.
  3. Tenant-isolation E2E: two test tenants, confirm neither's mobile session can see the other's orders/products/staff under any endpoint.

Given current coverage is minimal on both sides, the pragmatic sequencing is: tenant-isolation tests first (security), then the core POS create-sale integration test (correctness), then everything else — not a demand for full coverage before any further feature work.

CI/CD Strategy

Today: no CI/CD pipeline was found. The production app directory is a live git working tree (origin = a real GitHub repo) that appears to be pulled/pushed to directly on the VPS — deploys happen by editing or syncing the production server itself, evidenced by a recent commit made in that working tree ("sync: VPS server working tree state"). Recommended pipeline (proportionate to a 39-tenant SaaS — not enterprise-scale tooling)

git push (feature branch)
  -> CI: backend tests (phpunit) + mobile tests (flutter test) + lint
  -> merge to main
  -> CI: deploy to staging (backend) automatically
  -> manual smoke test on staging
  -> tag release -> CI: deploy to production (backend)

Backend

  • Move off "edit/pull directly on the VPS" to a proper deploy step: GitHub Actions (or similar) that SSHes in, pulls the tagged commit, runs composer install --no-dev, php artisan migrate --force, php artisan config:cache, and restarts PHP-FPM — all scripted and repeatable, never manual.

PART 23

Recommended Team Workflow

Because both clients already share one backend, the workflow that unblocks parallel work is API-contract-first, not "backend finishes, then hands off to web, then mobile":

  1. Before any cross-cutting feature (branches, offline, realtime) starts, backend and mobile (and web, if it turns out to consume the API too) agree the exact request/response shape in a shared document — even a lightweight OpenAPI/Swagger spec generated from the existing routes/api.php (tools like laravel-openapi or hand-written from the controllers already documented in §7) is enough; it doesn't need to be a heavyweight process for a team this size.
  2. Backend implements against the contract first, with API tests (§18) proving it, and deploys to staging (§16/§19).
  3. Mobile and web build against staging in parallel, not sequentially — once the contract is agreed in step 1, mobile doesn't need to wait for backend to finish; it can build against a mocked response matching the agreed contract and switch to the real staging endpoint when it's ready.
  4. Integration test on staging before either side merges to main.
  5. Release: backend deploys to production via CI/CD; mobile ships a build to internal testing, then store release — these do not have to be simultaneous as long as the API versioning discipline (§17) keeps old mobile versions working against v1 while new features roll out additively.

Where each role's throughput depends on another

  • Mobile is currently blocked less by backend than by mobile's own foundation gaps (env config, secure storage, offline architecture) — most of §7's endpoint gaps are "call an endpoint that already exists," not "wait for backend to build something." Prioritize unblocking mobile's own Phase 0/1 work immediately.
  • Backend's highest-leverage move is the tenant-isolation global scope (§12) and enabling the queue/scheduler (§9) — both are backend-only, unblock nothing on the client side directly, but reduce risk for everything built afterward; do them without waiting for a mobile ask.
  • Web's role is currently the biggest unknown (§9 item 1) — resolving whether it already goes through the API should happen early, since it determines whether "backend as single source of truth" is already true or needs a convergence project.

Given the team size implied by a 39-tenant SaaS, this likely means one backend developer, one web developer, one-to-two mobile developers can run Phases 0–2 largely in parallel once the contract-first habit is in place, converging for integration testing before each release rather than serializing through a strict backend→web→mobile handoff chain.

PART 24

Final Recommendation

Should we continue with the current mobile technology? Yes. Flutter, Riverpod, Dio, and auto_route are appropriate, modern choices; the app already has genuinely strong in-house engineering (the thermer receipt layout engine, the full HRM/inventory/KOT feature set) and is already integrated against the real production API, not a mock. There is no evidence here that would justify a rewrite in React Native, native Android, or anything else — the gaps found (offline, env config, release signing, token refresh) are integration and process gaps, not framework limitations.

How much of the mobile app is currently integrated? Substantially — roughly 80–85% of the shared operational surface (auth, catalog, POS, KOT, billing, inventory, customers, HRM, reports) already talks to the same backend and database as the web panel, because mobile was built directly against this API. The disconnect this audit was commissioned to check for — "two separate systems" — does not exist at the data layer. What's missing is concentrated in two whole modules (multi-branch, cash register) that were simply never built on mobile, plus a handful of specific endpoints (refresh-token, change-password, module-check) that exist but aren't called.

What must be changed?

  • Backend: enforce tenant isolation structurally (global scope), turn on the queue worker and scheduler, confirm/converge web's API usage, stand up staging + CI/CD.
  • Mobile: environment config, secure token storage + refresh-token adoption, real release signing, and — the largest genuine gap — offline order queueing.
  • Both: build out multi-branch and cash register on mobile as a deliberate scope decision, not leave them as accidental gaps.

What can remain unchanged? The core architecture: one Laravel backend, one MySQL database, Sanctum auth, the nwidart/laravel-modules structure, and the existing /api/v1 contract for the ~85% of endpoints already shared. No new backend, no separate mobile database, no new auth system.

What should be developed first? In order: (1) tenant-isolation hardening and CI/CD/staging — low effort, highest risk-reduction, unblocks everything else; (2) mobile's own foundation fixes (env config, secure storage, refresh-token, release signing) — small, self-contained, immediately reduces real operational risk; (3) multi-branch on mobile — the highest-value net-new feature since the backend already supports it; (4) offline order queueing — largest effort, sequence it once the foundation is solid.

How does Web + Mobile become one unified AppZetBilling platform? They largely already are one platform sharing one backend and database — the task ahead is completing and hardening that integration (closing the specific gaps in §6–§9 and §21), adopting API-contract-first collaboration between backend/web/mobile (§23) going forward, and resolving the one open architectural question that matters most: whether the web panel is already a client of its own API or has parallel logic that needs converging. That single confirmation should happen before any of the phased roadmap work in §20 begins.

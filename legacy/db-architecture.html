01 · Overview

What this database is

AppzetBilling is a single-database, shared-schema multi-tenant SaaS for restaurant and retail billing/POS. One MySQL database serves every tenant; isolation is enforced by a business_id column discipline rather than separate schemas. On top of a core schema, the Laravel application is extended with pluggable addon modules — HR, Multi-Branch, Cash Register, Custom Domain, Inventory, Online Store — each owning its own slice of tables.

03 · Multi-Tenancy

How one database serves every tenant

Shared database, shared schema, row-level isolation. There is one set of 97 tables; a tenant is a row in businesses, and isolation is enforced by a business_id column discipline — not by separate schemas or databases.

60 direct
14 transitive
22 global
Root — businesses itself Direct — own business_id column, 56 required + 5 nullable Transitive — one join from a tenant via a parent FK Global — no tenant linkage at all

56 of the 60 direct tables use business_id NOT NULL ON DELETE CASCADE — deleting a business deletes that tenant's row outright. Five are nullable by design: blogs, messages, testimonials (public-site content optionally attributed to a business, SET NULL), users (platform staff — superadmin/admin/manager — carry no business), and recipe_ingredients (nullable SET NULL, inconsistent with its sibling recipes — Finding 5).

Two isolation gaps at the database level

coupons.code — globally unique

Despite business_id NOT NULL, coupons_code_unique is a plain, non-composite key. Two tenants cannot use the same coupon code. Independently confirmed: the clone_business_catalog procedure's own comments skip cloning coupons for exactly this reason.

parties.phone — globally unique

parties_phone_unique is likewise non-composite. Two tenants cannot each have a customer or supplier with the same phone number.

Application-layer scopes (beyond the DB)

app/Models/Scopes/BranchScope.php adds branch-level filtering on top of tenant isolation once MultiBranchAddon is enabled and the user has an active_branch_id — enforced in Eloquent, not the database, so raw SQL bypasses it. app/Models/Scopes/DataManager.php is a separate ownership scope restricting queries to the current user unless they hold a named permission or are shop-owner.

Tenant provisioning — clone_business_catalog(source, target)

The only stored procedure in the database (database/scripts/clone_business_catalog.sql in the repo). A hands-on operational tool for spinning up a new tenant pre-populated from a template business, not something ordinary request traffic calls.

Validate

Both business IDs exist and differ; target already has a shop-owner user. Fails with SIGNAL SQLSTATE '45000' otherwise.

Guard idempotency

Refuses to run if the target already has categories rows — prevents double-cloning.

Copy catalog, remap keys

Inside one transaction: taxes, payment types, currencies, categories, menus, units (self-referencing base_unit_id fixed up in a second pass), kitchens, modifier groups, ingredients (stock reset to 0, party dropped), recipes, products (forced to the target's own owner), tables (booking state cleared), and more — using a temporary _clone_id_map(table_name, old_id, new_id) to rewrite foreign keys.

Never touch live data

Explicitly excludes coupons (global-unique bug above), sales/purchases and all transactional history, parties (real vendor/customer contacts), domains, business_gateways (live credentials).

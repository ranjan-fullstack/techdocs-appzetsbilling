1.2 Platform rules that shape the design

  • [[MO]] Meta (official Meta docs, not Petpooja): per-message pricing since 1 July 2025; marketing templates always charged; utility and authentication templates charged outside an open customer-service window and free inside it; service (customer-initiated) conversations free; non-template messages free; India INR billing localisation from 1 Jan 2026 with WABAs to be migrated to INR by 31 Dec 2026; rate cards published in INR (effective 1 Jul 2026). Source: Meta pricing docs.
  • [[TP]] Indicative INR rates from BSP blogs: marketing ≈ ₹0.86–0.88, utility/authentication ≈ ₹0.115–0.13 per message plus 18% GST and any BSP fee. One blog claims a change from 1 Oct 2026 making in-window utility messages chargeable; this conflicts with Meta's current page and is unverified. Always price from Meta's own rate card at build time.
  • [[TP]] Template languages: BSP documentation lists Odia among supported template languages — verify the exact template language code in Meta's official language list before building Odia templates. [[UNK]] until then.

1.4 Recommended controls

  • Tenant-specific WhatsApp numbers: tenant owns its WABA via Embedded Signup; AppZet stores encrypted tokens ([[REC]], consistent with the existing WhatsApp page).
  • Opt-in/opt-out: message_consents table (Part 07); honour "STOP" replies via the inbound webhook; separate consent for transactional vs marketing.
  • Delivery status + webhooks: verify signature, store raw event, idempotent on wa_message_id; update whatsapp_messages.status (sent/delivered/read/failed).
  • Usage billing: meter by category (usage_meters); plan includes an allowance, overage billed at cost plus margin — do not invent prices; see Part 10.
  • Rate limiting and quality: per-tenant sending caps, warm-up, and pause campaigns if the number's quality rating drops.
  • India compliance [[INF]]: keep an unsubscribe mechanism and consent records; get legal advice on DPDP Act obligations before marketing at scale (see Part 09).

3. Cloud + offline architecture (Phase 12)

3.1 Petpooja documented behaviour [[PO]]

See Part 04. Summary: "POS Local" keeps a database on a Windows machine (Bridge Server) at the outlet; counters and kitchen/captain devices connect through a master billing station; fully offline when co-located, up to 5 days when the server is separate; menu/price/settings/aggregator orders sync from the cloud when connectivity returns; scheduled local backups. The captain app and kiosk are stated to work offline with sync. Conflict resolution and duplicate prevention are [[UNK]].

3.2 AppZetBilling today [[V]]

Server-rendered cloud application on one VPS. No service worker for the POS, no IndexedDB, no local database, no sync engine, no idempotency keys on sale creation. If the internet drops, billing stops. Moreover, [[V]] AcnooInvoiceController::newInvoice builds the sales invoice number as (sales count + KOT count) + 1 per business: it is racy under concurrent sales, and because a sales.delete-all route exists, deleting rows can cause numbers to be re-issued. This must be fixed before any offline design because offline devices multiply the collision risk.

3.3 Proposed architecture [[REC]]

Level 0  Harden the online path (prerequisite)
  - server-side invoice sequence per outlet (row-locked counter)
  - client_uuid on every sale/KOT write (unique per business) -> duplicate-proof retries
  - queue worker + scheduler running

Level 1  Offline-tolerant web POS  (fast, no new hardware)
  - PWA + service worker caches app shell, menu, tables, taxes, payment types
  - IndexedDB "outbox": new sale / KOT / payment operations queued with client_uuid,
    device_id, local sequence, timestamp
  - reads served from cache; writes queued when offline, replayed in order on reconnect
    via POST /sync/batch (idempotent, per-operation result)
  - printing: local print agent works without internet (LAN printers)
  - limits: one active device per table while offline; bill number = outlet prefix +
    device prefix + local counter (reconciled to official number after sync)

Level 2  Outlet server (only for customers who need days offline / multi-device offline)
  - small local service (Windows/Linux mini-PC) with SQLite/MySQL mirror of one outlet
  - devices talk to the local server on the LAN; it syncs to the cloud (pull config,
    push transactions) with the same batch API
  - this is the closest analogue of Petpooja's Bridge Server; costly to support

Conflict and duplicate rules

  • Duplicates: unique (business_id, client_uuid) on sales/KOT/payments; a replay returns the original result.
  • Ordering: operations carry a device sequence; server applies per-entity in sequence; a table opened on two offline devices becomes a conflict item for a manager to merge (uses the same merge feature as table merge).
  • Master data (menu/price): server wins; device pulls changes?since= on reconnect.
  • Stock: deductions are applied on sync (ledger style); negative stock allowed offline, flagged after.
  • Payments: cash/UPI-manual payments queue offline; gateway payments require connectivity and are not attempted offline.
  • Retry: exponential backoff, visible "unsynced" counter, manual "sync now", alert if unsynced older than N hours.
  • Offline KOT: kitchen printer on LAN prints without cloud; a KDS needs LAN or connectivity (Level 2).
Priority note Offline is a CRITICAL capability gap against Petpooja's documented core offering and a top concern for low-connectivity towns, but Level 1 is roughly a quarter of engineering work and Level 2 is a product line of its own. Recommendation: build Level 0 immediately, Level 1 in Phase 1–2, and defer Level 2 until customer demand is measured.

Today: mobile has exactly one environment — a compile-time constant pointing at production (https://app.appzetsbilling.com). There is no dev/staging split anywhere in the mobile build, and the backend audit found no separate staging deployment on the VPS either (one nginx vhost, one .env, one database).

Development (localhost / LAN backend)
        |
Staging (staging.appzetsbilling.com — to be created)
        |
Production (app.appzetsbilling.com)

Recommended mobile change

Replace the hardcoded AppConfig.baseUrl with a build-time value injected via --dart-define=API_BASE_URL=... (read with String.fromEnvironment), with three VS Code/CI run configurations (dev/staging/prod). This is a small, self-contained change (one file, lib/app/core/static/app_config/_app_config.dart) and immediately removes the risk of engineers accidentally testing against live tenant data.

Recommended backend change

Stand up one staging environment: a second CloudPanel site (or subdomain vhost) pointed at a separate .env and a separate database (can be a periodic sanitized copy of production, or seeded fixture data — never a live copy with real customer data). Deploys to staging should be the first stop in the CI/CD pipeline (§19) before anything reaches production.

Rule going forward

No production URL, API key, or credential should ever be hardcoded directly into mobile source under version control — use --dart-define (or a build-time secrets mechanism, e.g. injected at CI build time) for all three environments, matching how the backend already keeps secrets in .env outside the repo.

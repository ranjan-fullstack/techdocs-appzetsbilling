Today: both sides are thinly tested. Mobile has 6 test files (mostly card widgets + one strong unit-test suite for unit-price conversion) against ~180+ page directories. The backend ships phpunit scaffolding but this audit did not find evidence of a meaningful test suite either (not confirmed either way — worth a direct follow-up with the backend team).

Backend

  • Unit tests: pricing/tax/discount calculation, stock deduction logic, plan-limit enforcement.
  • Integration tests: full request-response cycles for the core POS flow (create sale → stock deducted → transaction recorded → KOT created).
  • API tests: one test per endpoint group in §7 asserting shape + status codes, especially for the newly-adopted mobile endpoints (refresh-token, change-password, module-check).
  • Authorization/tenant-isolation tests (highest priority, currently absent): authenticate as tenant A, attempt to read/write tenant B's products/sales/parties/etc. by ID, assert rejection. This is the single most valuable test category for this product.

Web

  • Component tests for the Blade/Alpine interactive pieces (order builder, KOT board).
  • E2E (e.g. Laravel Dusk or Playwright) for the core POS flow through the actual UI.

Mobile

  • Unit tests: expand beyond the existing unit-price-calculator pattern to repository/parsing logic (model fromJson, permission-flag logic, cart/order total calculation).
  • API integration tests: repository methods against a mocked Dio client (add mocktail, currently absent) for each endpoint in §7.
  • Widget/UI tests for the core POS screens (order entry, KOT board, payment).
  • Offline tests (once §14 is built): queue-then-reconnect flows, duplicate-prevention via idempotency key.
  • Sync tests: order created on mobile appears correctly via the web-side API; order/KOT status changed via web is correctly reflected when mobile re-fetches/receives push.

End-to-end (cross-app), the highest-value additions given today's near-zero coverage

  1. Mobile creates an order → assert it's visible via the same read endpoint the web panel would use → assert stock decremented correctly.
  2. Web (or a second mobile session) updates KOT/order status → assert the first mobile session receives the update (push-triggered refetch, per §13) within an acceptable delay.
  3. Tenant-isolation E2E: two test tenants, confirm neither's mobile session can see the other's orders/products/staff under any endpoint.

Given current coverage is minimal on both sides, the pragmatic sequencing is: tenant-isolation tests first (security), then the core POS create-sale integration test (correctness), then everything else — not a demand for full coverage before any further feature work.

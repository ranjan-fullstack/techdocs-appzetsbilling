Web and mobile are already one platform, not two disconnected systems: both are verified clients of the same Laravel 10 backend, the same MySQL database, and — for roughly 80–85% of the shared operational surface — the same /api/v1 REST API. This is the headline finding of this audit and it changes the shape of the work ahead: the task is to complete and harden an integration that already exists, not to build a bridge between two divergent systems.

Mobile is a well-built Flutter app (Riverpod, Dio, auto_route) with genuinely strong custom engineering — including an in-house receipt-layout engine for thermal printing — and a nearly complete feature set matching the backend's tenant-facing modules (POS, KOT, kitchen, inventory, HRM, reports). Its real gaps are integration and operational, not architectural: no offline support, a single hardcoded production URL, a debug-signed release build, and several already-existing backend endpoints (token refresh, password change, module entitlement check) that the app simply doesn't call yet.

Backend is a Laravel 10 / Sanctum / MySQL SaaS (a customized "Acnoo" template, module-based via nwidart/laravel-modules) that already enforces multi-tenant isolation via business_id/branch_id scoping, though that isolation currently depends on per-controller discipline rather than a structural guarantee — the single highest-priority hardening item in this report. Queueing and the task scheduler are configured but not actually running in production; realtime broadcasting is scaffolded but not provisioned.

The two structural gaps — not incremental ones — are that Multi-branch and Cash Register are fully built backend modules with zero mobile presence. Everything else in the API mapping (§7) is either already shared or a small, well-scoped addition.

One open question materially affects how this roadmap should be sequenced and could not be resolved from a read-only pass alone: whether the web business panel calls its own /api/v1 API internally or runs parallel Blade-only business logic. Resolving this should be the very first step, before the phased roadmap (§20) begins.

Bottom line: continue with Flutter; do not rebuild the mobile app or the backend. Spend the first phase on tenant-isolation hardening, CI/CD, and mobile's own foundation (environment config, secure token storage, release signing) — all low-effort, high-leverage — then build multi-branch support on mobile and, as the largest single effort in this roadmap, offline order queueing.

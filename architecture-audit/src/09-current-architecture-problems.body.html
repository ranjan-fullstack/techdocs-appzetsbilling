Cross-cutting (Web + Mobile)

  1. Whether the web panel actually consumes its own REST API is unconfirmed. If the Blade admin/business panel has separate controllers that duplicate the business logic already in the Api/ controllers (rather than calling /api/v1/* internally), the team is maintaining tax/discount/stock logic in two places today — a correctness risk (the two can silently drift) independent of mobile. Action: have the web team confirm this directly, it changes how urgent an "API-first" refactor is.
  2. Tenant isolation is enforced by controller-level business_id filtering, not Eloquent global scopes. It works today, but it means every new controller/endpoint (including future mobile-only ones) must remember to scope its queries — one missed where('business_id', ...) is a cross-tenant data leak. This is the single most important thing to fix before scaling the API surface.
  3. No CI/CD pipeline. The production app root is a git working tree pulled/pushed to directly (git remote -v shows a live GitHub origin, recent commit made straight on the VPS). No staging environment, no automated tests gating a deploy, no build artifact.

Backend-specific

  1. Configured-but-inert infrastructure: queue (QUEUE_CONNECTION=database with no worker running), scheduler (schedule:run not in any crontab, so the low-stock check likely never fires), and realtime broadcasting (Pusher wired in code, no credentials, no broadcast server). None of these are wrong to have configured, but building new features that assume they work (e.g. "push a realtime order update") will silently do nothing today.
  2. Wide-open CORS (allowed_origins: ['*']) on api/*. Lower risk because the API is bearer-token, not cookie/credentialed, but still broader than necessary and worth tightening once mobile's environment strategy (§16) introduces named client origins/apps.
  3. LOG_LEVEL=debug in production and a world-writable storage/logs/ directory — minor but easy hardening fixes.
  4. Single API version (v1) with no versioning strategy yet. Fine today with one mobile client version in the wild, but there is no mechanism in place for the moment a mobile v2 needs a breaking change while v1 users still exist.

Mobile-specific

  1. No offline support at all for a restaurant POS — the single biggest functional gap for real-world restaurant conditions (spotty Wi-Fi, router restarts, busy service). See §14.
  2. Production APK is signed with the debug keystore. A real release-signing config needs to exist before a genuine Play Store/App Store release, independent of any architecture work.
  3. Hardcoded single production URL, no environment split. Every dev/staging test today either hits production or requires editing source and rebuilding — high risk of an engineer accidentally testing against live tenant data, and no safe way to test backend changes against a mobile build before release.
  4. No refresh-token usage, no FCM token-refresh sync, unencrypted token storage. The backend already exposes /refresh-token; mobile's auth session handling should be upgraded to use it rather than relying solely on a long-lived bearer token in plain shared_preferences.
  5. Two whole backend modules (Multi-branch, Cash Register) have no mobile presence. Not a bug, but a scope decision that should be made deliberately (§11/§20) rather than left as an accidental gap.

Net assessment

The good news for this audit: mobile and web are not two disconnected systems with separate databases or separate business logic — they already share one Laravel backend, one MySQL database, and (for the bulk of tenant-facing features) the same versioned REST API. The real work is tightening and completing an already-shared architecture, not building bridges between two divergent ones.

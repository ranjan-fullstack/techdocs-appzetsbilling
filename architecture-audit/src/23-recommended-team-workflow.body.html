Because both clients already share one backend, the workflow that unblocks parallel work is API-contract-first, not "backend finishes, then hands off to web, then mobile":

  1. Before any cross-cutting feature (branches, offline, realtime) starts, backend and mobile (and web, if it turns out to consume the API too) agree the exact request/response shape in a shared document — even a lightweight OpenAPI/Swagger spec generated from the existing routes/api.php (tools like laravel-openapi or hand-written from the controllers already documented in §7) is enough; it doesn't need to be a heavyweight process for a team this size.
  2. Backend implements against the contract first, with API tests (§18) proving it, and deploys to staging (§16/§19).
  3. Mobile and web build against staging in parallel, not sequentially — once the contract is agreed in step 1, mobile doesn't need to wait for backend to finish; it can build against a mocked response matching the agreed contract and switch to the real staging endpoint when it's ready.
  4. Integration test on staging before either side merges to main.
  5. Release: backend deploys to production via CI/CD; mobile ships a build to internal testing, then store release — these do not have to be simultaneous as long as the API versioning discipline (§17) keeps old mobile versions working against v1 while new features roll out additively.

Where each role's throughput depends on another

  • Mobile is currently blocked less by backend than by mobile's own foundation gaps (env config, secure storage, offline architecture) — most of §7's endpoint gaps are "call an endpoint that already exists," not "wait for backend to build something." Prioritize unblocking mobile's own Phase 0/1 work immediately.
  • Backend's highest-leverage move is the tenant-isolation global scope (§12) and enabling the queue/scheduler (§9) — both are backend-only, unblock nothing on the client side directly, but reduce risk for everything built afterward; do them without waiting for a mobile ask.
  • Web's role is currently the biggest unknown (§9 item 1) — resolving whether it already goes through the API should happen early, since it determines whether "backend as single source of truth" is already true or needs a convergence project.

Given the team size implied by a 39-tenant SaaS, this likely means one backend developer, one web developer, one-to-two mobile developers can run Phases 0–2 largely in parallel once the contract-first habit is in place, converging for integration testing before each release rather than serializing through a strict backend→web→mobile handoff chain.
